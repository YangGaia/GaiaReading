# GitHub 源码与版本发布

本指南用于用户明确授权的发布。常规开发继续在本地维护；本次授权的目标是 [lvlucky3641/GaiaReading_Lucky](https://github.com/lvlucky3641/GaiaReading_Lucky)，发布单个稳定版本 `v1.2.7`。这不授予后续版本自动上传或发布的权限。

本次按用户要求分两轮完成：先完成本地整理、双版本验证与上传材料准备，并汇报结束；待用户再次明确开始上传后，再集中提交源码、发布两个附件并核验。待发材料只保留在 `release-output/v1.2.7`，上传核验后清除，不提前执行远端写入。

## 本次发布清单

两个 Windows x64 便携 EXE 放在同一个稳定 Release 中，不拆成两个版本，不标记为预发布。

| 版本 | Release 附件名 | 音乐 |
| --- | --- | --- |
| Full59 | `GaiaReading_Lucky-1.2.7-Windows-x64-Full.exe` | 完整 59 首 FLAC |
| Lite3 | `GaiaReading_Lucky-1.2.7-Windows-x64-Lite.exe` | 仅 `1-01`、`1-05`、`1-08` 三首 FLAC |

版本号、标签、仓库源码和两个 EXE 必须一致。Release 说明列出版本差异、每个 EXE 的准确文件名、字节大小与 SHA-256，以及实际完成的验证。GitHub 自动生成的源码归档不包含音乐。

公开便携 EXE 可放在任意可写的本地磁盘，默认在 EXE 所在目录创建“数据”，即使 EXE 所在目录也叫“程序”，仍按此规则定位。移动便携版时一并移动旁边的“数据”。NSIS 启动时的解压目录使用进程的临时目录，不保证位于 EXE 旁；应用自己的持久资料和可控缓存默认放在“数据”内。

本地源码、自用目录式程序、构建、验证、暂存及备份继续遵守 F 盘约定。运行 Node、npm、Electron 或构建工具前，先在当前 PowerShell 中执行 `. ./scripts/dev-env.ps1`；本地验证显式指定独立的 F 盘数据和会话目录。原有自用“程序／开发／数据／备份”布局、启动入口及程序路径保持不变。

## 源码上传白名单

在 F 盘建立本轮专用 staging，从审核后的明确清单复制文件。不得直接推送日常工作副本的全部内容或旧 Git 历史。`.gitignore` 是补充检查，不能替代白名单，也不能从既有提交中移除已经出现过的文件。

允许准备的源码类别如下；每一项仍须逐文件核对：

| 类别 | 范围 |
| --- | --- |
| 仓库入口 | `README.md`、`LICENSE`、`.gitignore`，以及必要的 `AGENTS.md`、编辑器配置 |
| 构建清单 | `package.json`、锁文件及项目所需的文本构建配置 |
| 应用代码 | `src/` 下维护的源码与已核对的正式界面素材；排除生成的 vendor 库 |
| 维护与测试 | 可复用的 `scripts/`、`tests/`，以及不含个人内容的合成测试素材 |
| 文档与图标 | 经审核的 `docs/`、图标及其构建源文件；检查仓库内相对链接 |
| 音乐说明 | 音乐清单、文件名映射和恢复说明等文本；不包含 FLAC 或其他二进制音乐 |

必备的 `README.md`、`LICENSE` 和 `.gitignore` 缺一不可。README 应说明两个下载版本、便携数据位置、源码开发方式及音乐恢复步骤；软件许可证和第三方素材说明保持清晰，保留应有的许可和署名。

禁止上传个人书籍、书架、阅读进度、笔记、聊天记录、用户配置、加密凭据、`Local State`、个人备份、任何登录信息、个人环境文件、本地旧 `.git`、依赖、缓存、日志、临时档案、验证截图、构建 staging 和 EXE。不得推送所有本地分支、全部标签或镜像历史。二进制音乐只随本次 Release 的 EXE 提供，不进入源码仓库；需要从源码运行或重新构建时，按 [README](../README.md) 恢复音乐文件。

提交前检查 staging 的实际文件清单、暂存差异以及将要推送的提交范围，确认生成内容和私人数据均未进入历史。发布用的干净仓库不会替换或清空日常开发的本地 Git。

## 远端检查与提交

1. 先只读检查已有远端配置、目标仓库内容、默认分支、标签与 Releases，确认目标确实是用户指定仓库。已有远端指向其他地址时，不擅自改写。
2. 空仓库使用审核后的源码建立干净发布历史；已有内容的仓库以远端现状为基础，只合入本次授权内容，保留用户已有修改。遇到未知差异或同名标签、附件时先核对，不强推、不重置远端、不覆盖已有内容。
3. 将必备文档和白名单源码提交到发布用仓库，再核对远端提交与本次构建对应。维护记录、发布说明和终端输出中不得记录登录凭据。
4. 在确认的提交上使用 `v1.2.7` 标签，创建或完成本次明确授权的稳定 Release，并上传验证过的两个 EXE。需要中途准备时可使用草稿；后续版本必须另有用户明确要求。

若使用 CLI 登录，本轮临时配置保存在 F 盘专用目录中，不更改既有全局账号或登录配置。

## 构建与隔离验证

构建使用项目的便携脚本，并保持其自动发布关闭。完整音乐保留在本地正式素材目录中；Lite3 只在独立 staging 生成三首音乐的清单与文件，不删改完整音乐或日常源码清单。

两个 EXE 分开放在 F 盘的两个本轮验证目录，每个使用独立的数据、会话与临时目录。用合成书籍和测试配置验证，不读取日常书库，不使用用户真实接口凭据。

每个版本至少确认：

- EXE 正常启动、关闭和再次启动，书架、偏好和阅读进度能在自己的隔离档案中保存。
- 基本阅读、音乐播放、曲目选择和切歌正常；Full59 恰好 59 首，Lite3 恰好包含指定三首，界面清单与实际文件一致。
- 默认数据路径遵守便携 EXE 同级规则，显式测试档案保持独立；测试不会修改日常“数据”或原自用程序。
- 包内没有个人档案、书籍、凭据或测试文件；记录实际完成、失败或跳过的检查，不把未验证项记为通过。

所有验证结束、进程退出后，对最终上传的每个 EXE 计算 SHA-256 和字节大小。计算后若文件重新生成或修改，必须重新验证并计算。

## 远端确认与本地清理

上传完成不等于交付完成。先检查目标仓库、`v1.2.7` 标签、稳定 Release 状态、源码提交和两个附件名称、大小；再通过下载校验或远端提供的 SHA-256 摘要，与上传前记录逐项比对。发布说明保留最终校验值和必要的验证摘要。

远端确认成功后，关闭本轮进程，按本轮建立的明确清单清理：

- 发布源码 staging、发布用临时 Git、打包 staging、解压目录以及 Full59/Lite3 的本地重复 EXE 和下载校验副本。
- 本轮一次性脚本、截图、日志、详细检验报告、测试数据与临时启动入口；可复用构建和测试代码保留在源码中。
- 本轮临时 CLI 登录及其配置目录；只清理本轮身份，不注销已有全局账号，不触碰应用保存的用户凭据。
- 不再需要的可重建依赖和构建缓存，按 [维护指南](MAINTENANCE.md) 的限定范围处理。

删除前核对解析后的绝对路径、目录边界及链接目标，确认均属于本轮临时区域；不得按 EXE 扩展名、模糊中文名称或整棵交付目录批量删除。远端确认失败时保留尚未确认上传成功的产物，完成重试或明确报告阻碍。

最终不保留本轮发布产物的本地重复包。保留日常自用“程序”、正式源码和素材、本地 Git、完整用户数据，以及精简后的数据备份。备份仍保留一份固定迁移基准和最近两份常规备份；新的备份须先完整校验，再轮换旧包。应用内最多五份升级快照另行管理，详见 [维护指南](MAINTENANCE.md)。
